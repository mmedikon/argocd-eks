# EKS and Argo CD Installation using Terraform

Provision an **Amazon EKS** cluster (with a dedicated VPC and managed node group) and install **Argo CD** on it with Helm, all from a single Terraform configuration. This guide also covers validating the cluster, nodes and Argo CD pods, retrieving the initial admin password, and opening the Argo CD UI.



## Deploy

```bash
# 1. Initialise providers and modules
terraform init

# 2. Review the plan
terraform plan

# 3. Create everything (takes ~15-20 minutes)
terraform apply
```

Type `yes` when prompted. When the apply finishes, the outputs print the `kubectl` configuration command.

> **Tip:** If you want to bring up the cluster first and install Argo CD in a second step, run
> `terraform apply -target=module.eks` followed by a normal `terraform apply`.

## Validate the EKS Cluster and Nodes

**1. Configure `kubectl` to talk to the cluster**

```bash
aws eks update-kubeconfig --region us-east-1 --name argocd-eks-demo
```

**2. Check the cluster status in AWS**

```bash
aws eks describe-cluster --name argocd-eks-demo --region us-east-1 \
  --query "cluster.{Name:name,Status:status,Version:version,Endpoint:endpoint}" \
  --output table
```

Expected: `Status` is `ACTIVE`.

**3. Check cluster connectivity**

```bash
kubectl cluster-info
kubectl config current-context
```

**4. Verify the worker nodes are `Ready`**

```bash
kubectl get nodes -o wide
```

Expected output (example):

```
NAME                         STATUS   ROLES    AGE   VERSION
ip-10-0-1-187.ec2.internal   Ready    <none>   48m   v1.33.13-eks-3b4a6ca
ip-10-0-2-122.ec2.internal   Ready    <none>   47m   v1.33.13-eks-3b4a6ca
```

**5. Verify system pods are running**

```bash
kubectl get pods -n kube-system
```

`coredns`, `kube-proxy` and `aws-node` pods should all be `Running`.

**6. (Optional) Verify the managed node group**

```bash
aws eks list-nodegroups --cluster-name argocd-eks-demo --region us-east-1
```

## Validate Argo CD Pods

**1. Confirm the Helm release**

```bash
helm list -n argocd
```

**2. Check the namespace and pods**

```bash
kubectl get ns argocd
kubectl get pods -n argocd
```

Expected: all pods `Running` and `READY` (e.g. `1/1`):

```
NAME                                                READY   STATUS    RESTARTS   AGE
argocd-application-controller-0                     1/1     Running   0          32m
argocd-applicationset-controller-67c9b74747-fbn47   1/1     Running   0          32m
argocd-dex-server-dcb876fb6-q6krv                   1/1     Running   0          32m
argocd-notifications-controller-644488675f-ptfq5    1/1     Running   0          32m
argocd-redis-77b64d5f85-xvfmf                       1/1     Running   0          32m
argocd-repo-server-5d5999c545-n2577                 1/1     Running   0          32m
```

**3. Check the services**

```bash
kubectl get svc -n argocd
```

**4. Wait for the Argo CD server deployment to be ready**

```bash
kubectl rollout status deployment/argocd-server -n argocd
```

## Retrieve the Argo CD Admin Password

The initial password for the `admin` user is generated by Argo CD and stored in the `argocd-initial-admin-secret` secret.

**Linux / macOS**

```bash
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d; echo
```

```


> **Security:** After your first login, change the password (User Info -> Update Password) and delete the initial secret:
>
> ```bash
> kubectl -n argocd delete secret argocd-initial-admin-secret
> ```

## Access the Argo CD UI

Because the service type is `ClusterIP`, use `kubectl port-forward`:

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
```

Then open **https://localhost:8080** in your browser.

- Your browser will warn about a self-signed certificate. This is expected; proceed past the warning.
- Log in with `admin` and the password retrieved above.

Keep the terminal open while using the UI (press `Ctrl+C` to stop).

# Deploy a Sample Application with Argo CD UI (GitOps with GitHub)

This guide shows how to use **Argo CD** to deploy an **nginx** Deployment and Service on Amazon EKS, with the Kubernetes manifests stored in a **GitHub repository**. You will create the manifests repo, connect it to Argo CD, create the application through the **Argo CD UI**, then verify, update and clean up the deployment the GitOps way.

## Step 1: Create the GitHub Manifests Repository

**1. Create a new repository on GitHub**, for example `argocd-eks` (public is simplest; see Step 3 for private repos).

**2. Create the manifests:**
Repository layout:

```
argocd-nginx-demo/
└── manifests/
    ├── deployment.yaml
   
```

**3. `manifests/deployment.yaml`**



## Step 2: Open the Argo CD UI

In a terminal, start a port-forward (keep it running):

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
```

Open **https://localhost:8080**, accept the self-signed certificate warning, and log in:

- **Username:** `admin`
- **Password:** the value retrieved in the prerequisites

## Step 3: Connect the GitHub Repository

> **Public repo:** you can skip this step. Argo CD can pull public repositories without credentials, and the repo URL is simply entered in Step 4.

**For a private repo:**

1. In GitHub, create a **Personal Access Token** (Settings -> Developer settings -> Personal access tokens). Grant read access to the repository contents.
2. In the Argo CD UI go to **Settings -> Repositories -> + CONNECT REPO**.
3. Fill in:

| Field | Value |
|-------|-------|
| Connection method | `VIA HTTPS` |
| Type | `git` |
| Project | `default` |
| Repository URL | `https://github.com/<your-username>/argocd-nginx-demo.git` |
| Username | your GitHub username |
| Password | your Personal Access Token |

4. Click **CONNECT**. The repository should show **Connection Status: Successful**.

## Step 4: Create the Application in the UI

1. On the main page click **+ NEW APP**.
2. Fill in the form:

**General**

| Field | Value |
|-------|-------|
| Application Name | `sampleappl1` |
| Project Name | `default` |
| Sync Policy | `Automatic` (tick **Prune Resources** and **Self Heal**), or `Manual` to sync by hand |
| Sync Options | tick **Auto-Create Namespace** |

**Source**

| Field | Value |
|-------|-------|
| Repository URL | `https://github.com/<your-username>/argocd-nginx-demo.git` |
| Revision | `main` (or `HEAD`) |
| Path | `manifests` |

**Destination**

| Field | Value |
|-------|-------|
| Cluster URL | `https://kubernetes.default.svc` |
| Namespace | `default` |

3. Click **CREATE**.

The new application tile appears with status **OutOfSync** (manual sync) or begins syncing automatically (automatic sync).

## Step 5: Sync and Verify the Deployment

**In the UI**

1. Open the `nginx-demo` application tile.
2. If it shows **OutOfSync**, click **SYNC -> SYNCHRONIZE**.
3. Wait until the status shows **Healthy** and **Synced**. The resource tree displays the Service, Deployment, ReplicaSet and Pods.

**From the command line**

```bash
# Argo CD application object
kubectl get applications -n argocd

# Workload resources
kubectl get all -n ndefault

# Pods should be Running 1/1
kubectl get pods -n default -o wide

# Rollout status
kubectl rollout status deployment/nginx-deployment-n default


## Step 6: Access the nginx Application

**Option A: LoadBalancer (public)**

The AWS load balancer takes a few minutes to provision.

```bash
kubectl get svc nginx-service -n default
# copy the EXTERNAL-IP / hostname, then:
curl http://<EXTERNAL-HOSTNAME>
```

Open the same address in your browser to see the **Welcome to nginx!** page.

**Option B: Port-forward (private, no load balancer cost)**

```bash
kubectl port-forward svc/nginx-service -n nginx-demo 8081:80
```

Open **http://localhost:8081** or run `curl http://localhost:8081`.

## Step 7: Make a Change via Git

Scale the deployment and change the image through Git rather than `kubectl`.

```bash
# Edit manifests/deployment.yaml:
#   replicas: 2  ->  replicas: 3
#   image: nginx:1.27  ->  image: nginx:1.27.1   (optional)

git add manifests/nginx-deployment.yaml
git commit -m "Scale nginx to 3 replicas"
git push origin main
```

- **Automatic sync:** Argo CD detects the commit (polls about every 3 minutes by default) and applies it.
- **Manual sync:** the app shows **OutOfSync**; click **REFRESH** then **SYNC** in the UI.

Verify:

```bash
kubectl get pods -n default
```

You should now see 3 pods.

## Test Self-Heal and Rollback

**Self-heal (requires Automatic sync with Self Heal enabled)**

```bash
# Manually drift the cluster away from Git
kubectl scale deployment nginx-deployment -n default --replicas=1

# Watch Argo CD revert it to the Git-defined value
kubectl get pods -n default-w
```

Argo CD detects the drift and restores the replica count from Git.

**Rollback**

1. In the UI open the application and click **HISTORY AND ROLLBACK**.
2. Select a previous revision and click **Rollback**.

> Rollback requires auto-sync to be disabled. The cleaner GitOps approach is `git revert <commit>` followed by `git push`.




## Cleanup

Remove everything to stop incurring charges:

```bash
# If you created a LoadBalancer service, remove it first so AWS can delete the ELB/ENIs
kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "ClusterIP"}}'

terraform destroy
```

Type `yes` to confirm. Verify in the AWS console that the EKS cluster, NAT Gateway and EC2 instances are gone.

## Troubleshooting

| Problem | Likely cause / fix |
|---------|--------------------|
| `error: You must be logged in to the server (Unauthorized)` | Re-run `aws eks update-kubeconfig`. Make sure you use the same AWS identity that ran `terraform apply` (`aws sts get-caller-identity`). |
| `terraform apply` fails on the Helm release with a connection error | Cluster not ready yet. Run `terraform apply -target=module.eks`, then `terraform apply` again. |
| Nodes stay `NotReady` or the node group fails to create | Check the NAT Gateway/route tables and the node group status in the EKS console (Compute tab). |
| Argo CD pods `Pending` | Not enough node capacity. Check `kubectl describe pod <pod> -n argocd`; increase `desired_size` or use a larger instance type. |
| `argocd-initial-admin-secret` not found | The secret was deleted or Argo CD is still starting. Wait for pods to be ready, or reset the password via the `argocd-secret` (see Argo CD docs). |
| Port-forward: `address already in use` | Use another local port, e.g. `kubectl port-forward svc/argocd-server -n argocd 9090:443`. |
| `terraform destroy` hangs on VPC deletion | Leftover load balancers or ENIs created by Kubernetes. Delete the LoadBalancer services, then retry. |

| Problem | Likely cause / fix |
|---------|--------------------|
| Repo shows **Connection Failed** | Wrong URL, or the token lacks access. Check the repo URL ends with `.git` or matches the clone URL, and that the PAT can read the repo. |
| App stuck **OutOfSync** | Manual sync policy. Click **SYNC**, or enable automatic sync. |
| **`ComparisonError` / path does not exist** | The `Path` field does not match the repo folder. Use `manifests` and confirm the files were pushed to the branch in **Revision**. |
| **`namespace not found`** on sync | Enable **Auto-Create Namespace** (`CreateNamespace=true`) or create it: `kubectl create ns nginx-demo`. |
| App **Healthy** but Service `EXTERNAL-IP` is `<pending>` | The load balancer is still provisioning. Wait a few minutes, check `kubectl describe svc nginx-service -n nginx-demo`, and confirm public subnets are tagged `kubernetes.io/role/elb`. |
| Pods `ImagePullBackOff` | Wrong image name/tag, or nodes have no outbound access (check the NAT Gateway). |
| Changes in Git not picked up | Argo CD polls every ~3 minutes. Click **REFRESH** (or **Hard Refresh**) in the UI, or configure a GitHub webhook for instant sync. |
| Self-heal does not revert manual changes | Confirm `selfHeal: true` is set under `syncPolicy.automated`. |
